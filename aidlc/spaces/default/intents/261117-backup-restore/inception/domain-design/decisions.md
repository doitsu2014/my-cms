# Architecture Decision Records — Backup & Restore

## ADR-001: Register domain_backup_restore as the owner of backup metadata

- **Context** — Durable job metadata is required before returning `202`. Existing architecture delegates migrations to registered domain services, but no current domain owns backup job/package lifecycle. The human confirmed a separate Rust crate `domain_backup_restore` registered inside the existing gateway process; it is not a separately deployed service. Real-data staging remains disabled until TLS, private encryption, finite limits and restart-safe cleanup are verified.
- **Decision** — Add `domain_backup_restore` as a Rust crate and register its `DomainService` in the gateway manifest. The crate owns the migration and backup-only job/package/audit metadata schema. Package/staging bytes belong to a separate `PackageObjectStoreAdapter` boundary for a future configured private object store; no provider is selected and U1 does not write real data or staging bytes. The crate uses the gateway's shared `DomainContext`/PostgreSQL connection and the Administrator mount. CMS, GoTrue and Storage source data remain owned by existing domains/platforms.
- **Consequences** — The workspace manifest, gateway dependencies/manifest, registration, migration ownership and tests must be updated together after this revised design is approved. No independent deployment process, new cloud resources or ownership transfer of source data is implied.
- **Alternatives Rejected** — (1) Put backup metadata/migration in `domain_posts`, `domain_user`, `domain_media` or `domain_seo`: those domains do not own the backup job lifecycle. (2) Store jobs only in process memory: fails durable-before-acceptance and restart semantics. (3) Create a separately deployed service/process: conflicts with the confirmed same-gateway interpretation and localhost-only scope. (4) Store package bytes in BackupPersistence's metadata database: conflates metadata with large object payloads and is not approved.

## ADR-002: Add a dedicated BackupRestore orchestration component

- **Context** — Backup/restore spans admin operations, job lifecycle, My-CMS database, GoTrue/Auth, Storage and archive integrity. Requirements call for server-side authorization, asynchronous status, explicit destructive confirmation, best-effort consistency and package verification. Existing boundaries place posts in `domain_posts`, identity in GoTrue/domain_user integration and media in `domain_media`/Supabase Storage. No complete backup feature currently exists.
- **Decision** — `BackupRestoreDomain` owns job lifecycle/state policy, configured source/target selection, manifest/package metadata, preflight, idempotency/concurrency policy, audit references and success/failure aggregation. It is implemented by the `domain_backup_restore` crate. `BackupAdminApi` provides protected routes; `BackupWorker` is a bounded in-process worker invoked through a one-way runtime handle; `BackupPersistence` owns metadata persistence/migration; adapters isolate DB, Auth, Storage and object-byte boundaries.
- **Consequences** — Centralizes cross-system safety rules and avoids duplicating package semantics in each domain. Requires explicit API/worker/persistence contracts, route registration and adapter capability checks. The crate becomes a gateway-registered domain and must respect existing shared pool/auth composition.
- **Alternatives Rejected** — (1) Put export logic independently in each existing domain: distributes consistency, package and failure semantics across domains. (2) Let admin UI access Supabase services directly: exposes service capabilities/credentials and cannot securely coordinate server-side jobs. (3) Put all work in a synchronous HTTP request: unsuitable for large backups and long restore operations.

## ADR-003: Preserve source-data ownership; BackupRestore owns only backup metadata

- **Context** — My-CMS, GoTrue/Auth and Storage have existing ownership boundaries. Human clarification rejected transfer of source-data ownership after the initial response was ambiguous: the backup component should own only job/package metadata while existing domains/platforms retain data ownership.
- **Decision** — `domain_backup_restore` owns `BackupJob` (operation=`backup|restore`), `BackupPackage` metadata and one-to-many `BackupAuditEvent` records. It obtains source data through narrowly scoped adapters/exporters/importers. My-CMS business entities remain owned by their current domains; GoTrue identities remain platform-owned; Storage objects remain Storage-owned. A distinct `RestoreJob` is not introduced unless later Functional Design identifies restore-specific lifecycle attributes not represented by the operation-specific job.
- **Consequences** — Ownership remains aligned with existing architecture and limits migration blast radius. Adapter capabilities and allowable schema/bucket scope must be explicit and verified. Cross-domain restore cannot assume one common transaction. Package bytes and private staging bytes are not metadata entities and remain behind `PackageObjectStoreAdapter`.
- **Alternatives Rejected** — (1) Move CMS/Auth/Storage entities into the backup crate: contradicts existing ownership contracts and couples unrelated domain evolution. (2) Let gateway directly manipulate every schema: bypasses domain ownership and fragments backup metadata lifecycle. (3) Add RestoreJob without restore-only attributes: duplicate job identity/state with no proven need.

## ADR-004: Use protected API + bounded worker with durable saga/state machine

- **Context** — Backup/restore jobs may be long-running; multiple stores are involved and there is no shared transaction across PostgreSQL, GoTrue and object storage. Requirements accept best-effort backup consistency, require progress/status and prohibit partial success signaling.
- **Decision** — The protected API validates actor and configured source/target, persists a job through `BackupPersistence` and returns only after durable commit. `BackupRestoreDomain` passes an opaque job identity through a one-way gateway runtime handle to `BackupWorker`; the worker executes adapter ports and persists guarded states. Restore is a later saga/recovery flow with component-specific rollback or `recovery-required`; no global atomicity is claimed. U1 does not claim that Tokio scheduling alone gives restart recovery and does not write real source/staging bytes until the approved storage and cleanup gates are implemented.
- **Consequences** — API requests remain bounded and job metadata can survive process restarts once the new domain-owned migration is implemented. Durable leases, timeout, retries, target locks and recovery still require detailed later design. Best-effort capture must be stated in each package. A verified recovery point is required before target mutation; otherwise restore is refused.
- **Alternatives Rejected** — (1) One transaction across database/Auth/Storage: unsupported assumption across independent systems. (2) Independent adapters without aggregate job state: cannot provide reliable status, idempotency or truthful terminal outcome. (3) Keep an HTTP connection open for the entire operation: fragile for large/slow jobs and client/network timeouts. (4) Make the worker call back into the domain service: creates a circular dependency; the domain instead supplies a one-way runtime dispatch handle and owns policy.
