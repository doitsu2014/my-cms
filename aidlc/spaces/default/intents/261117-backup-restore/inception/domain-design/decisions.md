# Architecture Decision Records — Backup & Restore

## ADR-001: Add a dedicated BackupRestore orchestration component

- **Context** — Backup/restore spans admin operations, job lifecycle, My-CMS database, GoTrue/Auth, Storage and ZIP integrity. Requirements call for server-side authorization, asynchronous status, explicit destructive confirmation, best-effort consistency and package verification. Existing boundaries place posts in `domain_posts`, identity in GoTrue/domain_user integration and media in `domain_media`/Supabase Storage. No complete backup feature currently exists.
- **Decision** — Create a logical `BackupRestore` component responsible for job lifecycle/state machine, source/target selection via configured IDs, manifest/package orchestration, preflight, idempotency/concurrency policy, audit references and success/failure aggregation. Add a protected `BackupAdminApi`, `BackupWorker`, persistence for backup-specific metadata and focused adapters for database, Auth and Storage. This is a logical component decomposition only; deployment topology is deferred.
- **Consequences** — Centralizes cross-system safety rules and avoids duplicating package semantics in each domain. Requires explicit API/worker/persistence contracts and adapter capability checks. BackupRestore becomes a new component that must coordinate with gateway auth/composition.
- **Alternatives Rejected** — (1) Put export logic independently in each existing domain: distributes consistency, package and failure semantics across domains. (2) Let admin UI access Supabase services directly: exposes service capabilities/credentials and cannot securely coordinate server-side jobs. (3) Put all work in a synchronous gateway request: unsuitable for large backups and long restore operations.

## ADR-002: Preserve source-data ownership; BackupRestore owns only backup metadata

- **Context** — My-CMS, GoTrue/Auth and Storage have existing ownership boundaries. Human clarification rejected transfer of source-data ownership after the initial response was ambiguous: the backup component should own only job/package metadata while existing domains/platforms retain data ownership.
- **Decision** — `BackupRestore` owns `BackupJob`, `RestoreJob`, `BackupPackage` metadata and audit references. It obtains data through narrowly scoped adapters/exporters/importers. My-CMS business entities remain owned by their current domains; GoTrue identities remain platform-owned; Storage objects remain Storage-owned.
- **Consequences** — Ownership remains aligned with existing architecture and limits migration blast radius. Adapter capabilities and allowable schema/bucket scope must be explicit and verified. Cross-domain restore cannot assume one common transaction.
- **Alternatives Rejected** — (1) Move all CMS/Auth/Storage entities into BackupRestore: contradicts existing ownership contracts and would couple the backup feature to unrelated domain evolution. (2) Let gateway directly manipulate every schema: bypasses domain ownership and makes future changes fragile.

## ADR-003: Use protected API + worker with durable saga/state machine

- **Context** — Backup/restore jobs may be long-running; multiple stores are involved and there is no shared transaction across PostgreSQL, GoTrue and object storage. Requirements accept best-effort backup consistency, require progress/status and prohibit partial success signaling.
- **Decision** — The protected API validates actor and configured source/target, persists a job through BackupPersistence and dispatches BackupWorker. Worker invokes BackupRestore use cases; BackupRestore coordinates adapters and persists state through the persistence interface. Restore uses a saga/recovery model with component-specific rollback or `recovery-required`; the design does not claim global atomicity. Idempotency and target-level concurrency are part of orchestration.
- **Consequences** — API requests remain bounded and job state can survive process restarts. Durable persistence, leases/timeouts, retries, target locks and recovery operations require detailed design. Best-effort capture must be stated in each package. Initial localhost runtime is expected to use Tokio tasks in the gateway process, but restart/lease semantics must be resolved in Functional Design; this does not define production deployment. A recovery point is required before target mutation if available; otherwise restore is refused.
- **Alternatives Rejected** — (1) One transaction across database/Auth/Storage: unsupported assumption across independent systems. (2) Independent adapters without aggregate job state: cannot provide reliable status, idempotency or truthful terminal outcome. (3) Keep an HTTP connection open for the entire operation: fragile for large/slow jobs and client/network timeouts.
