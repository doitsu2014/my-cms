## Context

`apps/ducth-dev-website/src/components/posts/ArticleProse.tsx` renders a
`dangerouslySetInnerHTML` of the localized post body inside a single
`<div className="article-prose">`. The TipTap editor in
`apps/web/src/app/admin/components/inputs/rich-text-editor/tiptap-editor.tsx`
emits HTML with the following node / mark extensions enabled:

- **Block**: `StarterKit` (paragraph, headings 1–6, blockquote, bullet /
  ordered list, list item, code block, hard break, horizontal rule),
  `CodeBlockLowlight` (`<pre class="code-block">`),
  `Table` (`<table class="tiptap-table">` + thead/tbody/tr/th/td),
  `TaskList` / `TaskItem` (`<ul data-type="taskList">` with
  `<li data-type="taskItem">`).
- **Inline mark**: `Underline` (`<u>`), `StarterKit` bold/italic/strike,
  `Highlight` (`<mark>`), `Subscript` / `Superscript` (`<sub>` / `<sup>`),
  `TextStyle` + `Color` (`<span style="color:…">`), `Link`
  (`<a class="text-primary underline">`).
- **Node**: `Image` (`<img class="rounded max-w-full h-auto">`),
  `Youtube` (`<div class="iframe-wrapper">` + `<iframe class="rounded max-w-full">`).

The current `.article-prose` rules in
`apps/ducth-dev-website/src/App.css` cover only the historical StarterKit
subset. The TipTap extensions above therefore render with no contract CSS and
fall back to the browser defaults, which is what the user reported.

The canonical spec at `openspec/specs/website-design-system/spec.md` already
mandates the full contract and explicitly forbids Tailwind Typography
("`SHALL NOT depend on Tailwind Typography`"). A prior fast-fix attempt
replaced the contract with Tailwind Typography's `prose` class and added
`--tw-prose-*` variables; it was rejected because it violated the spec and
was fully reverted before this change was scaffolded.

The CSS processor is `lightningcss` (via `@rsbuild/core` and
`@tailwindcss/postcss`). The class set generated by the Tailwind v4
`@tailwindcss/typography` plugin is the only thing that brings `prose` /
`prose-lg` into the production bundle, and we deliberately do not consume
it on the public reader.

## Goals / Non-Goals

**Goals**

- Make every TipTap node and mark the editor can produce look intentional
  inside the article body without changing the JSX of `ArticleProse`.
- Keep the ink-tide palette (`--fg`, `--ink-deep`, `--accent`, `--surface`,
  `--muted`, `--border`, `--font-display`, `--font-mono`) the single source
  of truth for the prose contract.
- Honour the canonical spec: no `prose` / `prose-lg` class on `ArticleProse`,
  no `--tw-prose-*` variables in the public-reader CSS.
- Add a regression test that exercises a TipTap document with at least one
  table, one task list, one inline mark, and one image, all wrapped in
  `.article-prose`.
- Sync the stale "uses `prose prose-lg`" wording in
  `apps/ducth-dev-website/design/02-typography.md` and `08-components.md`
  with the spec.

**Non-Goals**

- Switching the public reader to Tailwind Typography (forbidden by spec).
- Changing the TipTap editor config or the `HTMLAttributes` of any
  extension; the contract must work with the HTML the editor already emits.
- Adding a new npm dependency, a new design token, or a new global selector
  outside `.article-prose`.
- Touching the admin app's prose (the admin uses its own DaisyUI prose
  through `apps/web`).
- Visual redesign — only completeness of the contract is in scope.

## Decisions

### D1. Keep the contract under a single selector (`.article-prose`)

- **Why**: The spec wording "`article body SHALL use the `.article-prose`
  contract`" is explicit. Adding a second class would split the contract and
  make the spec wording less testable.
- **Alternative considered**: introduce a `.article-prose` parent + a
  `.article-prose-body` child (e.g. `prose prose-lg article-prose`).
  Rejected — the spec forbids Tailwind Typography, and splitting the
  contract on a single rendered wrapper is unnecessary.

### D2. Add the missing rules in `App.css` rather than `tailwind.config.ts`

- **Why**: Every existing `.article-prose` rule lives in `App.css`; the
  Tailwind v4 config is a stub that only declares content scanning.
  Adding the new rules to `App.css` keeps the contract in one file and
  avoids relying on Tailwind's `@apply` (which would require opting the
  selector into `@layer components`, adding complexity for no benefit).
- **Alternative considered**: declare the new tokens in `tailwind.config.ts`
  and rely on `@apply` inside `App.css`. Rejected — the `.article-prose`
  contract predates the v4 plugin setup and has never been migrated; doing
  so now expands scope without fixing the user-visible symptom.

### D3. Target the exact HTML the editor emits

- **Why**: The rules must match the production output, not a hypothetical
  clean output. Each rule references the actual class / data-attribute
  TipTap sets (`class="tiptap-table"`, `data-type="taskList"`,
  `data-type="taskItem"`, `class="code-block"`, etc.) so future editor
  changes that drop those classes will surface as a test failure rather than
  silent visual breakage.

### D4. Reject the Tailwind Typography approach

- **Why**: The canonical spec at
  `openspec/specs/website-design-system/spec.md` says "The prose contract
  SHALL NOT depend on Tailwind Typography." This is an explicit product
  decision, not an oversight. The rejected approach also forces every
  contributor to remember to set `--tw-prose-*` tokens for new themes.
- **Alternative considered**: add Tailwind Typography purely as a private
  utility (e.g. wrap the body in `not-prose` and use the plugin on
  children). Rejected — it would still leave the dependency in
  `package.json` and `@plugin '@tailwindcss/typography';` in `App.css`,
  contradicting the spec.

### D5. Sync the design docs in the same change

- **Why**: `02-typography.md` and `08-components.md` still describe the
  prose line as "uses `prose prose-lg`" which contradicts the spec. Leaving
  the docs stale would re-introduce the same confusion on the next fix
  attempt. The doc edit is a single line in each file and is reversible.

## Risks / Trade-offs

- **[Risk]** The new selectors might still miss a TipTap node the admin
  adds in the future. → **Mitigation**: the new test in
  `src/pages/pages.test.tsx` exercises a representative TipTap document
  (table + task list + inline mark + image) so future additions are
  visible at code review and the editor's own `HTMLAttributes` give a
  one-line search target when the contract must grow.
- **[Risk]** `lightningcss` already fragments one `.article-prose code`
  rule into two because of the `color-mix(in oklch, …)` value. → **Mitigation**:
  keep the new rules in plain CSS (no `color-mix` if a single literal
  works) and verify the production bundle after the change.
- **[Risk]** The `.article-prose` contract grows large. → **Mitigation**:
  group new rules under a comment header so the rule set remains readable
  and the spec's "define a `.article-prose` contract" wording still
  describes a single, coherent block.
- **[Trade-off]** Tests must import the live TipTap HTML; we do not
  introduce a snapshot file. The expected HTML is short, the assertion is
  an exact-match on the wrapper class, and snapshotting TipTap output
  would make the test brittle to TipTap upgrades that are otherwise
  invisible to the public reader.

## Migration Plan

1. Land the CSS additions in `apps/ducth-dev-website/src/App.css` together
   with the test additions in `src/pages/pages.test.tsx`. No DB migration,
   no env var, no deployment flag.
2. `rsbuild build` in `apps/ducth-dev-website` to refresh
   `dist/client/static/css/index.*.css`. The hash will change; the
   `index.html` template picks it up automatically.
3. Roll back by reverting the three files (`App.css`,
   `src/pages/pages.test.tsx`, the two design markdown files). The change
   is purely additive so a partial deploy is safe; the only failure mode
   is the contract not covering a new TipTap node, which surfaces in
   review, not in production.
4. After archive, the delta specs at
   `openspec/changes/fix-public-blog-prose-styling/specs/...` merge into
   `openspec/specs/website-design-system/spec.md` and
   `openspec/specs/website-reader-experience/spec.md` via
   `openspec-sync-specs`.

## Open Questions

- None. The spec wording is unambiguous, the editor output is enumerable,
