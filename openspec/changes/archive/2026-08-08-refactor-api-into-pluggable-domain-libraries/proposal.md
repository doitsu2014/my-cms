## Why

The API is difficult to extend because the current `cms` package, `apps/api/application_core`, and `migration` package are broad shared containers rather than domain boundaries. The observed pain points are: `bin/my-cms-api` carries bootstrap, routing, state, storage, GraphQL, and middleware setup; `application_core`, `migration`, `presentation_models`, `common`, and `api` are dumped into one application surface; and cross-domain imports couple posts to tags/categories and the gateway directly to application-core internals. The current source demonstrates this in `apps/api/src/bin/my-cms-api.rs` (a 331-line bootstrap/router module), `apps/api/src/lib.rs` (a single `AppState` aggregating all domain concerns), and `apps/api/application_core/src/commands/*`. The previously proposed shared `domain_foundation` + shared `application_core` + isolated `migration` crate shape did not solve the problem — it kept the shared kernel and only renamed the boxes. The user has redirected the refactor toward three concrete outcomes: a single Cargo-injectable **domain interface** contract crate, **self-contained per-domain packages** (starting with `domain_posts`), and **independently deployable** domain microservices that can either run standalone or be composed behind a thin gateway.

## What Changes

- Add a single **standalone, reusable, publishable contract crate** — `domain_interface` — that exposes a dyn-compatible `DomainService` trait and the small set of stable types (`DomainContext`, `Mount`, `RouteRegistration`, `HealthDescriptor`, `MigrationDescriptor`) needed to register routes, run migrations, and observe health. It has no concrete domain implementation dependency and is `publish = true` so any domain can inject it as a Cargo dependency.
- Introduce `domain_posts` as a **self-contained Cargo crate with both `lib` and `bin` targets**. It owns every responsibility a domain needs to operate: HTTP adapters, application-layer command handlers, domain infrastructure (error, response, time helpers, extensions), the post-relevant generated entities, the post migrations, the integration clients (Supabase auth, Supabase Storage, OpenAI, pgvector), the GraphQL contribution, and the tests. No shared `domain_foundation`, no shared `application_core` for posts, and no shared central `migration` crate for posts.
- Make `domain_posts` a **deployable microservice**: its `bin` target boots a standalone Axum server with its own auth/CORS/cookie/body-limit/OpenTelemetry layers, its own database connection, its own migrations (via `cargo run -p domain_posts -- migrate`), and its own health endpoint. The same `domain_posts` crate is also registered as a `Box<dyn DomainService>` inside the gateway when the composed deployment mode is chosen.
- Add a thin **gateway composition crate** that imports `domain_interface` and the domains it composes, holds a `Vec<Box<dyn DomainService>>`, iterates the manifest to build the three Axum routers (`Mount::Public`, `Mount::Protected`, `Mount::Administrator`), applies the auth/CORS/cookie/body-limit/Otel layers, and serves the listener. The gateway does not import domain commands, entities, DTOs, storage clients, or business rules. The legacy `application_core` and `migration` crates remain as **transitional compatibility shims** for categories/tags/media/users/ai until each is extracted in a follow-up change.
- Define per-domain migration ownership: each domain owns its `MigrationDescriptor`s and exposes an idempotent runner (`domain_posts::migrations_cli::run`). The orchestrator is a small helper inside `domain_posts` (for standalone mode) and a sibling helper inside `gateway` (for composed mode). Migration identities (`m20240409_151952_release_100`, `m20250330_151455_release_110`, `m20260126_040610_release_300`, `m20260531_000001_pgvector`) are preserved exactly so the database `up` history is unchanged.
- Preserve existing REST paths, GraphQL paths, auth roles, error mappings, and external integration behavior. The composed gateway serves the same `/`, `/health`, `/healthz`, `/media/**`, `/categories/**`, `/posts/**`, `/tags`, `/users/**`, administrator bucket/migration paths, and both `/graphql/**` paths as today.
- Provide a new-domain scaffold by **copying the `domain_posts` crate** into `domain_<name>/`, renaming the crate, replacing `posts` identifiers, and appending a `Domain<Name>Service` to the gateway's manifest. No shared `domain_foundation` template crate is created; `domain_posts` is the canonical reference.

## Capabilities

### New Capabilities
- `domain-service-interface`: Stable, publishable, dyn-compatible contract crate that exposes only trait + types, no concrete domain implementation imports; may be a Cargo dependency of any domain.
- `domain-post-service`: Self-contained Blog Post Service boundary — owns its own REST adapters, application-layer command handlers, presentation models, domain infrastructure, generated entities, translations, OpenAI/pgvector integration, GraphQL contribution, migrations, and tests; can be deployed as a standalone microservice or composed behind the gateway.
- `api-gateway-bootstrap`: Thin Cargo composition crate that registers domains through the `DomainService` trait, builds the three Axum routers, applies cross-cutting layers, and serves the listener. Supports both gateway-composed and standalone domain runtime modes without weakening existing auth/CORS/cookie/body-limit/tracing/behavior.

### Modified Capabilities
- None. This is intended to be behavior-preserving; existing capability requirements remain applicable.

## Impact

Affected source includes `apps/api/Cargo.toml`, `apps/api/src/bin/my-cms-api.rs`, `apps/api/src/lib.rs`, `apps/api/src/api/**`, `apps/api/src/common/**`, `apps/api/src/presentation_models/**`, `apps/api/application_core/src/**`, `apps/api/migration/src/**`, and `apps/api/test_helpers/src/lib.rs`. New workspace members will be added under `apps/api/`: `domain_interface` (publishable contract), `domain_posts` (lib + bin, self-contained), and `gateway` (thin composition bin whose binary is `my-cms-api`). The legacy `cms` lib, `application_core`, and `migration` crates become transitional compatibility shims and are removed in follow-up changes after categories/tags/media/users are extracted as their own self-contained domains. Client-visible routes and schemas must remain compatible. The refactor changes crate imports, entity generation locations, migration ownership, startup composition, build graph, test fixtures, and developer documentation, but introduces no intentional database, HTTP, or migration-identity change.
