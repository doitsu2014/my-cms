# WU-10 known limitations

1. **Descoped residual (RK-15 owner disposition, TS-34 part, TS-41 runtime part).** The full gateway boot with posts, seo and backup on one database was not exercised in this unit. Owner disposition: descope. What was tested: backup runtime start after migrations with the backup migrator only (Docker test `backup_runtime_starts_after_migrations_and_composed_api_is_ready`, `seaql_migrations_backup` recorded). The existing `migration_tests` (posts and seo) still pass. `domain_seo` and `domain_posts` were not modified. TS-34 "upgrade beside posts and seo" and the runtime part of TS-41 stay open residuals for a later owner decision.
2. **RK-16: no merge to `main`.** U1 stays on its feature branch until a separate release decision. Backup migrations are registered unconditionally (no conditional-registration code), so any image built from this branch creates `backup_*` tables on `migrate up` and on every gateway start, whether or not backup is enabled. A failure in those migrations would abort gateway start.
3. **Slow header delivery (T-13 residual).** The timeout layer sits inside the router. A client that dribbles its headers is handled by hyper before the router; 408 covers slow inner processing only. A 408-before-401 ordering is not observable (auth decides from the Authorization header alone).
4. **Header limit counts name plus value bytes only.** It does not count the request line, header separators or HTTP/2 framing, and hyper's own header limits still apply below it.
5. **Compose HOST.** `deployments/docker-swarm/apps/.env.example` sets `HOST=0.0.0.0`, so backup is forced disabled (`NON_LOOPBACK_BIND`) in that stack. Not changed here (outside the unit's files); the README says so.
6. **Scheduler driver is minimal.** `spawn_backup_scheduler` wakes `scheduler_step` every 60 s; there is no separate database probe. When admissions are closed, each wake runs the recovery order (reconcile, cleanup, sweep, reopen). It is covered by one Docker test (tick and recovery) and not by a long-running test.
8. **Storage-root forbidden paths.** `BackupConfig` documents that consumers should call `validate_storage_root` with the forbidden (static assets, web build) paths; the gateway knows none of them, so only the shape, link and privacy checks run (unchanged from WU-01).
9. **Runtime start failure is not retried.** If `Runtime::start` fails (for example the namespace lock is held), backup stays `BACKUP_NOT_READY` until the gateway restarts; the scheduler does nothing for a never-started runtime.
10. **Docker test flakiness under load.** (Worker run.) Two of three full ignored-suite runs had one to two unrelated `domain_backup` Docker tests fail in the testcontainer harness (`unexpected response from SSLRequest`, `PortNotExposed`) while the host load average was about 9 with other workers sharing Docker; the third run, with the same command, passed 215 of 215. Logs: `green-workspace-ignored-run1-flaky.log`, `green-workspace-ignored-run2-flaky.log`. No WU-10 code is involved in those tests.
11. **Existing README mentions.** README now has an env section, but `deployments/docker-swarm/apps/.env.example` and the Helm values were not given `BACKUP_*` examples (outside Files).
12. **Test-only convenience.** `compose_routers(services, ctx)` is `#[cfg(test)]`; production uses `compose_routers_with_limits`.
13. **Worker driver cadence.** Queued jobs are claimed within about 2 s by a polling driver; there is no push notification from create to worker. The driver only runs while admissions are open, so during an outage queued jobs wait (and the sweeper fails them after 600 s, as designed).
14. **Pre-existing clippy findings (not WU-10):** `gateway/src/backup_cli.rs` dead-code warnings and the `match previous` single-pattern lint in an existing `migrate_cli.rs` test.
